# 02 — 協定規格

## 1. 來源

協定定義是 LLVM 的公開原始碼，不需要逆向：

* `llvm/lib/RemoteCachingService/RemoteCacheProto/compilation_caching_cas.proto`
* `llvm/lib/RemoteCachingService/RemoteCacheProto/compilation_caching_kv.proto`

本 repo 的 `proto/` 目錄是這兩個檔案的原樣副本（來自 `swiftlang/llvm-project`
的 `next` 分支）。參考實作在
`llvm/lib/RemoteCachingService/RemoteCacheServer/LLVMCASCacheProvider.cpp`，
用戶端在 `llvm/lib/RemoteCachingService/CAS/GRPCRelayCAS.cpp`。

Xcode 的 plugin 是 Swift 寫的 gRPC client，可以從 binary 直接確認它連的方法：

```bash
strings -a /Applications/Xcode.app/Contents/Developer/usr/lib/libToolchainCASPlugin.dylib \
  | grep '^/compilation_cache_service'
```

```

```

## 2. 傳輸層

* **gRPC over HTTP/2**，`application/grpc+proto`。
* 監聽在 **Unix domain socket**。plugin 選項名稱是 `remote-service-path`，
  值就是 socket 的檔案路徑（不是 URL，也不能填 `host:port`）。
* 沒有 TLS、沒有認證。要跨機器必須自己做本機中繼（見
  [05-Rust-Server](05-Rust-Server.md)）。
* 編譯產物動輒數 MB，**server 必須調高 gRPC 訊息上限**，預設 4 MiB 絕對不夠。
  本實作預設 512 MiB。

## 3. CASDBService

```proto
service CASDBService {
  rpc Get(CASGetRequest) returns (CASGetResponse) {}    // 帶 refs 的完整物件
  rpc Put(CASPutRequest) returns (CASPutResponse) {}
  rpc Load(CASLoadRequest) returns (CASLoadResponse) {} // 只有 blob，不含 refs
  rpc Save(CASSaveRequest) returns (CASSaveResponse) {}
}

message CASDataID { bytes id = 1; }
message CASObject { CASBytes blob = 1; repeated CASDataID references = 2; }
message CASBlob   { CASBytes blob = 1; }
message CASBytes  { oneof contents { bytes data = 1; string file_path = 2; } }
```

### 語意要點（含實測結論）

**CAS id 是不透明的。** `Put` / `Save` 的請求裡沒有 id 欄位 —— **是 server 決定 id**。
client 把 `Save` 回傳的 id 原封不動存起來，下次用同一串 bytes 呼叫 `Load`。
LLVM 的參考 server 回傳的是 `llvmcas://<hex>` 這種字串，本實作回傳 32 bytes 的
raw digest；兩者 plugin 都接受。

> 實測佐證：plugin 本身的 digest 是 `luxon.blake2b`（65 bytes，開頭 `0x00`），
> 而我們回傳 32 bytes 的 BLAKE3，整個 round-trip 依然成功。所以
> **不需要複製 LLVM 的雜湊演算法**，只要自洽即可。

**`CASBytes` 可能是檔案路徑。** client 可以用 `file_path` 送出大 blob，省下一次
複製。這條路徑是 client 的本機檔案系統，所以：

* 單機部署：直接讀該檔案。
* 跨機器：中繼層必須先把檔案內容讀出來內嵌，才能往上游送。

**`write_to_disk` 只是提示。** proto 註解明講 server 可以照樣回傳 `bytes`。
本實作預設一律內嵌回傳；設定 `--blob-dir` 時才會真的落檔並回 `file_path`。

**找不到物件不是錯誤。** 回 `outcome = OBJECT_NOT_FOUND`，不要回 gRPC error
status，否則在 `COMPILATION_CACHE_ENABLE_STRICT_CAS_ERRORS=YES` 時會讓建置失敗。

**digest 長度探測。** LLVM 的 `GRPCRelayCAS` 建立連線時會先送一次
`Save("")`，用回傳 id 的長度當作本服務的 digest 長度，上限 80 bytes。
所以 **id 長度必須固定**，不能因內容而變。

### Get/Put vs Load/Save

| | 帶 refs | 用途 |
| --- | --- | --- |
| `Put` / `Get` | ✅ | 完整的 CAS 節點（data + 參照） |
| `Save` / `Load` | ❌ | 純 blob |

Xcode 27 的 plugin 實測只用 `Save` / `Load`（物件圖的結構被編進 KV value 裡），
但 `Put` / `Get` 仍應實作，別的 client（例如 LLVM 自己的 `GRPCRelayCAS`）會用。

## 4. KeyValueDB

```proto
service KeyValueDB {
  rpc GetValue(GetValueRequest) returns (GetValueResponse) {}
  rpc PutValue(PutValueRequest) returns (PutValueResponse) {}
}

message Value { map<string, bytes> entries = 1; }
message GetValueRequest  { bytes key = 1; }
message GetValueResponse {
  enum Outcome { ERROR = 0; KEY_NOT_FOUND = 1; SUCCESS = 2; }
  Outcome outcome = 1;
  oneof contents { ResponseError error = 2; Value value = 3; }
}
message PutValueRequest  { bytes key = 1; Value value = 2; }
message PutValueResponse { optional ResponseError error = 1; }
```

這就是 action cache。對 server 而言：

* `key` 是不透明 bytes（Xcode 27 plugin 送的是 65 bytes 的 `luxon.blake2b` digest）。
* `Value.entries` 整張 map 原樣存、原樣取。**不要解析內容**；Xcode 27 實測只有
  一個 key `"value"`，但這是實作細節，可能改變。
* miss 回 `KEY_NOT_FOUND`，不要回 gRPC error。

實際的 `entries["value"]` 裡放的是一棵序列化的物件樹：小節點的 data 直接內嵌，
大節點則換成 `CASDBService.Save` 拿到的 id。可以用 `xxd` 直接看出來：

```
0a 3f                             # entries
  0a 05 "value"                   #   key
  12 36                           #   value (bytes)
     0a 19 (0a 17 "…root payload")  #     根節點
     12 19 (0a 17 "…leaf payload")  #     被參照的節點
```

## 5. CAS Plugin API（llcas_*）

編譯器不直接說 gRPC，它透過 LLVM 的 C plugin ABI 呼叫 dylib：

* 標頭檔：`llvm/include/llvm-c/CAS/PluginAPI_types.h`、`PluginAPI_functions.h`
* Xcode 27 內附的 plugin 回報版本 **0.1**
* 參考實作（Swift）：`swiftlang/swift-build` 的 `Sources/MockToolchainCASPlugin/`

對接遠端服務時只有這幾個函式重要：

| 函式 | 說明 |
| --- | --- |
| `llcas_cas_options_set_ondisk_path` | 本機 CAS 目錄 |
| `llcas_cas_options_set_option(…, "remote-service-path", <socket>)` | **指定遠端服務** |
| `llcas_cas_get_hash_schema_name` | Xcode 27 回 `luxon.blake2b` |
| `llcas_cas_store_object` / `llcas_cas_load_object` | CAS 讀寫 |
| `llcas_actioncache_put_for_digest` / `..._get_for_digest` | action cache 讀寫，`globally` 參數即「是否走遠端」 |

`tools/plugin_probe.c` 就是直接呼叫這組 API 的最小程式，用來在不跑編譯器的情況下
驗證 server。

## 6. 已知限制（實測）

**大節點不能有參照。** 對一個 data 很大、同時又有 refs 的物件呼叫
`llcas_actioncache_put_for_digest`，plugin 會回：

```
makeRemoteValue: data part is large with non-zero references
```

真實的編譯結果天然符合這個形狀（小的根節點指向大的輸出 blob），所以不影響實用，
但自製測試資料時要注意。

**沒有刪除／GC 協定。** 協定沒有 evict、TTL、quota 的概念，容量管理完全是 server
自己的事。
